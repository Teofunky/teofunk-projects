## 1. Цель и контекст

Клуб Алексея Козлова (kozlovclub.ru) — московский джаз-клуб, 4 сцены, ~175–180 концертов в месяц. 85% трафика — мобильные. Текущий сайт — афиша-список с клиентским JS-рендерингом (плохо для SEO и парсинга).

Строим новый **мобильный продающий сайт** с рекомендательной механикой уровня маркетплейсов (Ozon/WB/Кинопоиск): гость приходит не за «концертом», а за вечером. Продукт ведёт его как заботливый арт-директор: квиз за 60 секунд → 3 рекомендации с человеческой причиной → билет за 3 тапа → маршрут вместо билета (Pass, «ещё один вечер»).

**Главный принцип (ТРИЗ-разрешение противоречия):** клубу нужно продвигать резидентов и вечера с низкой заполняемостью, гостю нельзя это показывать. Коммерческий приоритет встроен в скоринг с малым весом и на поверхности всегда переупакован в заботу: «выбор арт-директора», «редкий вечер».

**Деплой:** параллельно основному сайту (поддомен, напр. `new.kozlovclub.ru`), на основном — кнопка «Новая версия сайта». Нулевой риск для текущих продаж, A/B-сравнение конверсии.

**KPI (из стратегии):**
- Quiz→Ticket ≥ 22% (бенчмарк культурных маркетплейсов — 14%)
- Второй билет за 30 дней ≥ 35%
- Доля Pass/маршрутов в выручке ≥ 18%

## 3. Ticketscloud: данные

Документация: https://ticketscloud.readthedocs.io (v1 REST) и https://doc.ticketscloud.org (v2).

- База: `https://api.ticketscloud.org`
- Авторизация: заголовок `Authorization: key <TC_API_KEY>`
- События: `GET /v1/resources/events` — коллекция; `GET /v1/resources/events/:id` — объект. Ответ содержит `title`, даты (`lifetime`), площадку, `media` (обложки), наборы билетов (sets) с ценами и количеством.
- Остатки/цены билетов также доступны через `GET /v1/services/simple/events` (simple-сервис для распространителей; в v2 это gRPC tc-simple — использовать только если REST v1 не отдаст остатки).

**Задача первой сессии Claude Code:** написать `scripts/tc-probe.ts` — дёрнуть `/v1/resources/events` с ключом, сохранить сырой JSON в `fixtures/`, и по факту реальной структуры зафиксировать маппинг полей в `lib/tc/map.ts`. Не проектировать маппинг вслепую — сначала посмотреть реальный ответ.

Fallback, если ключ не отдаёт нужное: скрейпер основного сайта Playwright'ом (там те же события с виджет-ссылками TC, event_id извлекается из кода виджета).

**Определение сцены:** в TC сцена, скорее всего, зашита в названии/площадке/тегах события. Правило маппинга (уточнить по реальным данным): `Main Stage | Мансарда/Mansarde | The Beat | Unplugged` — искать подстроку в venue/title/description. Событие без распознанной сцены помечается `stage: unknown` и попадает в афишу без чипа сцены.

## 4. Модель данных

```prisma
model Event {
  id            String   @id            // TC event id
  title         String
  program       String?                 // подзаголовок программы
  stage         String                  // main | beat | mans | unpl | unknown
  startsAt      DateTime
  durationMin   Int?
  priceMin      Int                     // ₽, минимальная цена сета
  priceMax      Int?
  seatsLeft     Int?                    // остаток, если отдаёт API
  rawDescription String?                // исходный текст с сайта/TC
  sellText      String?                 // продающий текст от Claude (≤ 220 зн.)
  whyLine       String?                 // одна строка «почему вам» (≤ 90 зн.)
  tags          Json                    // {mood:[], who:[], level, format}
  isResident    Boolean  @default(false)
  commercialWeight Int   @default(0)    // 0–10, руками или правилом low-fill
  curatorPick   Boolean  @default(false)
  imageOriginal String?
  imageCard     String?                 // 720×920 обработанная
  imageHero     String?                 // 1280×880 обработанная
  tcWidgetId    String                  // для встраивания виджета
  contentHash   String                  // хэш исходника — триггер регенерации
  updatedAt     DateTime @updatedAt
}
```

## 5. Пайплайн Claude API: тексты

Модель: `claude-sonnet-4-6`. Вызывается **только** когда `contentHash` изменился. Ответ строго JSON, валидируется zod'ом; при невалидном ответе — 1 ретрай, затем событие публикуется с исходным текстом (деградация мягкая).

Системный промпт (зафиксировать в `lib/ai/prompts.ts`):

```
Ты — редактор джаз-клуба Алексея Козлова. Перепиши описание концерта.

ЖЁСТКИЕ ПРАВИЛА:
1. Используй ТОЛЬКО факты из исходного текста. Ничего не выдумывай:
   ни регалий, ни программ, ни имён. Если факта нет — не пиши его.
2. sellText: до 220 знаков, тёплый уверенный тон, без восклицаний,
   без слов «уникальный», «незабываемый», «потрясающий».
3. whyLine: одна строка до 90 знаков — человеческая причина пойти,
   в духе: «Хорошо для свидания. Узнаваемые мелодии, мягкий вокал».
4. Теги выбирай только из словарей:
   mood: first | calm | deep | dance | wild
   who: solo | date | friends | work
   level: первый визит | понятный вход | атмосферный | для знатоков | редкий формат
5. Ответ — только JSON: {"sellText","whyLine","tags":{"mood":[],"who":[],"level"}}
```

Стоимость: ~180 событий × 2 обновления/мес × ~700 токенов ≈ копейки; лимитов не упрётся.

## 6. Пайплайн изображений (sharp)

Никакой AI-генерации лиц артистов (репутационные и правовые риски). Единая эстетика — программной обработкой при импорте:

1. Скачать оригинал (из TC `media` или с сайта)
2. `imageCard` 720×920 (3:4 под карточки полок), `imageHero` 1280×880 — умный кроп `sharp().resize({fit:'cover', position:'attention'})`
3. Тонировка: лёгкий тёплый grade (`modulate({saturation:0.92})` + мягкий наложенный градиент «свет рампы» снизу — уже заложен в дизайне CSS-слоем, в файл не запекать)
4. Вывод: WebP q=80 + AVIF, в `/public/img/events/` (или S3-совместимое хранилище)
5. Событие без картинки → генеративный CSS-плейсхолдер из прототипа (тёмный с янтарным светом) — уже готов

## 7. Скоринг рекомендаций

```
score =
  moodMatch        × 30   // пересечение quiz.mood и event.tags.mood
+ whoMatch         × 20
+ budgetFit        × 15   // в бюджете: +15; выше бюджета: −40
+ dateProximity    × 10   // ближайшие 7 дней — линейное затухание
+ firstVisitFit    × 10   // если mood включает first и level подходит
+ commercialWeight × 1    // 0–10: резиденты, низкая заполняемость
+ seatsUrgency     × 5    // остаток ≤ 10 мест
```

Коммерческий вес ≤ 10 — не может продавить рекомендацию против настроения, но при равных поднимает нужный клубу вечер. **На поверхности никогда не показывается**; бейдж-причины: «Лучший выбор» (топ-1), «Выбор куратора» (curatorPick), «Редкий вечер» (commercialWeight>0), «Чуть смелее» (остальные).

Реализация уже есть в прототипе (`score()`, `reason()`) — перенести 1:1, заменив синтетику на БД.

## 8. Экраны и маршруты

Эталон каждого экрана — прототип v3. Переносить дизайн-систему точно.

| Маршрут | Экран | Источник в прототипе |
|---|---|---|
| `/` | Главная: hero дня, CTA квиза, цитата куратора, полки | scr-home |
| `/podbor` | Квиз 3 шага (mood → who → budget) | scr-quiz |
| `/podbor/result` | 3 рекомендации + «вся афиша» | scr-recs |
| `/afisha` | Плотный список, чипы-фильтры (сцены, свидание, цена) | scr-afisha |
| `/sceny` | 4 сцены | scr-stages |
| `/e/[id]` | Концерт: почему пойти, тарифы TC, trust-блок, sticky CTA | scr-concert |
| `/e/[id]/done` | После покупки: «ещё вечер», Pass | scr-done |

Состояние квиза — URL-параметры + localStorage (возврат к подборке без повторного квиза). Полки главной: «Сегодня в клубе» (startsAt = сегодня), «Хорошо для свидания» (tags.who содержит date), «Выбор куратора» (curatorPick).

**Покупка:** bottom-sheet с встроенным виджетом Ticketscloud по `tcWidgetId` (скрипт виджета — тот же, что на основном сайте; взять embed-код оттуда). После события `order done` от виджета (или по закрытию шторки с подтверждением) — редирект на `/e/[id]/done`.

## 10. SEO · Аналитика · 152-ФЗ

- SSR/ISR: каждый `/e/[id]` — полноценный HTML с `Event` schema.org (JSON-LD: name, startDate, location, offers.price) → бесплатный рост из поиска, чего лишён основной сайт
- `sitemap.xml`, `robots.txt`, OG-картинки (из imageHero)
- Аналитика: **только Яндекс.Метрика + VK Pixel** (уроки 152-ФЗ уже пройдены на основном сайте: никаких Meta Pixel / Google Analytics). Цели: quiz_start, quiz_done, widget_open, order_done
- Персональные данные покупателя обрабатывает виджет Ticketscloud — на нашей стороне ПД не собираются (нет форм). Cookie-баннер — стандартный, только Метрика

## 11. Хостинг и деплой

Требование: Node.js-хостинг, стабильно доступный из РФ. Варианты по убыванию предпочтения:
1. **Timeweb Cloud / Selectel VPS** + Docker + Caddy (автоSSL) — полный контроль, РФ-локация (плюс к 152-ФЗ и скорости)
2. Рег.ру / REG Cloud App Platform
3. Vercel — быстрее всего для превью-стадии, но риски доступности из РФ; допустим только для внутреннего демо

CI: GitHub → Actions → деплой по push в main. Sync-пайплайн — cron в том же контейнере (`node scripts/sync.ts` каждые 15 мин) + ручной запуск.

DNS: `new.kozlovclub.ru` → сервер. На основном сайте — кнопка в шапке.
