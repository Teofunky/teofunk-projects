# JSON и точные дубли

Рабочая схема: `schemas/issue.schema.json`, версия 1.1. Исходные редакционные файлы v1 сохранены без правок в `editorial/`. Схема 1.0 принимается для совместимости; `event_id` выводится из `story_group_id`. В схеме 1.1 event_id обязателен. Импорт не загружает URL и не выполняет программные команды из текста.

`POST /wp-json/ezhednevny-standard/v1/import`

- HTTPS на рабочем сервере. WordPress Application Password пользователя с es_import либо штатная cookie-аутентификация с REST nonce.
- `Content-Type: application/json`.
- До 262144 байт; глубина JSON до 32; 0–7 статей в черновике; 4–7 для допуска.
- На статью до 12 источников, 40 фактов, 40 абзацев, 10 цитат. Общие строки до 20000 символов; дополнительные лимиты заголовка, лида, выжимок и ID в валидаторе.
- До 10 запросов импорта в минуту на пользователя. Лимит атомарный, одна служебная строка на пользователя.
- Неизвестные поля отклоняются, publication.status должен быть draft, edition_number — null. Прислать publish/approved нельзя.
- Для изменённого повторного импорта: `If-Match: "текущая_версия"`; при отсутствии 428, устаревшей версии 409.
- Точная повторная полезная нагрузка возвращает прежний ID с `unchanged:true`. Форматирование JSON (отступы) не имеет значения; порядок полей и некоторые равнозначные формы не нормализуются как семантическое равенство.
- Рекомендуется `import_id`: 1–128 символов `[a-zA-Z0-9_.:-]`. Повтор этого ключа с изменённым содержимым — 409. Для новой редакции входных данных нужен новый import_id и If-Match.
- Человек коснулся выпуска — импорт его больше не перезаписывает. Любой ранее опубликованный выпуск защищён даже после снятия с публикации. Повтор совершенно идентичного ранее принятого импорта лишь возвращает квитанцию, ничего не меняя.
- Каждый импорт сохраняется в собственном журнале. Разные параллельные запросы на одну дату не создают два номера.

Ответ: `{ "id": 123, "version": 1, "status": "draft", "unchanged": false }`; ETag содержит версию. Публикационного REST endpoint нет. Публичный `/latest` содержит только утверждённую читательскую проекцию.

## Идентичность и связи

| Поле | Область уникальности / назначение |
|---|---|
| edition_date | Уникальная дата выпуска в газете |
| import_id | Уникальный ключ операции во всей газете |
| article.id | Уникален внутри выпуска; входит в неизменяемый slug с датой |
| event_id | Единое событие для статей разных источников и последующих развитий |
| story_group_id | Совместимый ID сюжетной группы из редакционного v1 |
| source.id | Локальный ID источника в статье; на него ссылаются факты |
| source.publication_id | Необязательный ID публикации у источника; сравнивается в пределах домена |
| source.content_hash | Необязательный SHA-256 исходного текста; 64 строчных hex-символа |
| previous_article_ids | Slug ранее опубликованных собственных материалов, например `2026-10-20-samara` |
| development_note | Публичное объяснение существенного нового факта; проверяется человеком |

События, публикации источников, вхождения источников в статьи, отпечатки и связи находятся в отдельных таблицах. Связи и отпечатки существуют в слоях draft/public. Рабочая правка не удаляет опубликованную историю. У событий и публикаций предусмотрено расширяемое metadata, у связей — method/confidence для будущего распознавания; в 0.3.0 ИИ их не заполняет.

Нормализация URL: регистр схемы/домена, удаление фрагмента, удаление utm_*, fbclid, gclid, yclid, mc_cid, mc_eid, сортировка оставшихся параметров. Завершающий слеш, содержательные параметры и пути не объединяются без доказательства: сервер ничего не запрашивает. Canonical исходного сайта, редиректы и AMP-зеркала автоматически не распознаются.

Текст статьи сравнивается после удаления HTML, декодирования сущностей, свёртки пробелов и приведения к нижнему регистру при доступном mbstring. Полный одинаковый текст — блокер. Одинаковые события, заголовки, URL, внешние ID и хеши источников — предупреждения с конкретными предыдущими статьями. Для допуска нужны предыдущие slug и новый факт. Одно слово в новом тексте не считается машинным доказательством значимости развития: это решает редактор.

Внутри номера одинаковые event_id, тексты, URL, ID и хеши публикаций источников между разными новостями блокируют допуск. Повтор одного canonical URL, внешнего ID или хеша публикации внутри одной статьи отклоняется при валидации. Факт `verified_independent` требует двух независимых редакционных цепочек; две перепечатки с одной dependency_group не проходят. Правдивость групп и соответствие источника самому утверждению проверяет человек.

Проверки охватывают весь опубликованный архив. До 51 результата на индексный запрос используются для ограничения нагрузки; слишком широкие совпадения блокируют допуск и требуют уточнения. Схожая формулировка, перевод, перефразирование, неточный event_id и семантический повтор без общего идентификатора не гарантированно обнаруживаются. Это область будущего сборщика, а не заявленная возможность 0.3.0.

## Что подтверждает редактор

Три положительных статуса: verified_primary, verified_independent, attributed_single. unverified блокирует. Для каждого существенного факта требуется хотя бы один существующий source_id. Источники должны иметь дату проверки; будущие даты проверки и публикации не принимаются для выпуска. Дата будущего события/релиза допустима и хранится отдельно.

Редактор видит все источники, факты, исходные цитаты, приватные замечания, права, связи и социальные версии. Подтверждение записывается вместе с user_id, временем, хешем текущего материала и письменным результатом проверки. Любое сохранение материала требует нового подтверждения. Снятие блокеров номера не подтверждает статьи автоматически.

Плагин не доказывает истинность текста, полноту списка существенных фактов, реальную независимость СМИ, права на фото или корректность перевода цитат. Нет встроенного доступа к полным первоисточникам и проверки HTTP-доступности ссылок. Эти ограничения видны редактору и не маскируются статусом «проверено ИИ».
