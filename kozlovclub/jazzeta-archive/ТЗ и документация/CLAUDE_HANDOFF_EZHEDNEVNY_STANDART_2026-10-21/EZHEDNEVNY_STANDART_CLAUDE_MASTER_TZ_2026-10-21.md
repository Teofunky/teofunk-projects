## 1. Конечный продукт: что увидит читатель и что получит владелец

Издание в классической газетной эстетике, не «ИИ-агрегатор», не блог и не автоматическая лента всех ссылок. Один качественный выпуск в день (при наличии действительно значимых событий): преимущественно 4–7 **собственных** русскоязычных коротких материалов с точными источниками, культурным контекстом, сохранёнными датами, умеренной интонацией. Чтение всего номера — примерно 3–5 минут. Приоритет — значимость, достоверность, разнообразие, оригинальная литературная редактура.

Читательские элементы: выразительная первая полоса с одним главным материалом; другие новости разной значимости; навигация «Россия», «Мир», «Новые записи» и иные рубрики по наличию; статьи с постоянными адресами; архив по датам и номерам; ссылки на источники; штатная шапка/подвал Клуба; мобильная версия; A−/100%/A+; ночной режим; до пяти карточек 4:5 для соцсетей; Telegram-дайджест. Соцматериалы содержательно совпадают с утверждёнными статьями; ни одна ссылка не должна вести на ещё не опубликованную статью.

Ежедневно редактору: очередь собранных материалов, лог происхождения, ранжирование, проверочные заметки, предупреждения о повторах, собранный JSON и **новый черновик WordPress**. Владелец просматривает каждую статью, проверяет источники и права на изображения, исправляет ошибки, одобряет номер и вручную публикует.

Публичная газета может быть открыта только отдельным действием владельца после приёмки. Наличие утверждённого выпуска в режиме `closed` не открывает его посетителям автоматически.

## 2. Непреложная безопасность действующего сайта

- **Никаких изменений чужих структур БД, темы, чужих плагинов, афиши, заказов, TicketsCloud/касс и билетов.** Плагин вправе использовать собственные `es_*` таблицы, свои настройки/роли в рамках штатного WordPress API, собственные виртуальные URL и зарегистрированные права. Такие системные записи в `wp_options`/`wp_usermeta` нужно учитывать в плане обновления.
- Не «улучшать» весь WordPress, PHP, Redis или кэш без отдельного письменного разрешения и теста. Не менять `functions.php`, `header.php`, меню темы, `.htaccess`, `wp-config.php` и настройки W3 Total Cache автоматически.
- Разработка/нагрузочные испытания только на копии. Перед каждым обновлением сделать проверенную резервную копию файлов + БД с доказанным путём восстановления. Если доступа для полного теста нет — честно перечислить непроверенное.
- Самые чувствительные сценарии: не допустить смешения приватных/публичных кэшей, публикации без владельца, перезаписи ручной редакции, падения главной страницы клуба, увеличения времени загрузки афиши и ошибок билетных сервисов.
- Не отправлять в LLM пароли, сессии WordPress, исходную БД клуба, персональные данные клиентов, приватные черновики, персональные данные пользователей; Beget требует обезличивать данные в запросах.
- Запрет создания публичного REST endpoint для кнопки «Опубликовать» или «Принудительно заменить опубликованное». У сборщика — минимальная роль `Газета — импортёр` / `es_import`, отдельный Application Password. Никогда не использовать сессию/пароль владельца.
- Любое извлечение сайтов ограничивать разрешёнными доменами, HTTPS, лимитами байт и времени, запретом доступа к внутренним IP/локальным именам; учитывать SSRF, DNS rebinding, XML entity abuse, HTML/JS-инъекции и prompt injection из публикаций.
- Отказ 403/429, robots.txt, лицензионное или paywall-ограничение означает отказаться/отложить получение и отметить источник, **не обходить** их через прокси, «другой User-Agent» и т. п.

### 5.1 Дополнительные тематические источники — не утверждены автоматически

Разработчик может предложить **отдельным списком на согласование** авторитетные источники гитарной/блюзовой/фанк-сцены и производителей оборудования, а также конкретные RSS/API; примеры направлений: Guitar World, Premier Guitar, MusicRadar, Blues Rock Review, официальные страницы Guitar Summit/Crossroads/NAMM. Но **не включать их в производство без проверки домена, RSS/API, условий доступа, новостной ценности и согласия владельца**. Не утверждать, что все названные площадки разрешают извлечение текста.

## 6. Производственный цикл — от обнаружения до готового черновика

```
[Разрешённые RSS/API/открытые источники]
       ↓ Fetch + идентичность источника + robots/terms/rate limits
[Хранилище входящих метаданных / ссылок / времени получения]
       ↓ Нормализация ссылок, дат, языка, авторов, тега, региона
[Кандидаты + события + архив 14 дней + конфликт/дубли]
       ↓ Классификация/ранжирование (дешёвая LLM или детерминированно)
[Очередь 4–7 потенциально важных сюжетов]
       ↓ Получение ДОПУСТИМОЙ фактической базы + проверка утверждений
[Структурированные утверждения ↔ доказательства ↔ уровень доверия]
       ↓ Генерация оригинального русского текста редакторской LLM
[Фактчекинг / дополнительная независимая проверка / стилистическая редактура]
       ↓ Строгая schema 1.1 + технические правила WordPress
[JSON-черновик + редакционный журнал + соцвыжимки]
       ↓ Отдельный REST POST через es_import (никогда не publish)
[Редакционная панель WordPress → человек → вручную утвердить]
       ↓
[Публичный выпуск + архив + готовые карточки/дайджест]
```

### 6.1 Сканирование

- Планируемая цель: новый **черновик к 09:00 МСК**. Стартовый исполнитель предусмотрен около 08:00 МСК; если задерживается, система сигнализирует и не делает вид, что номер готов. Не гарантировать 09:00 до измерения времени реальных источников.
- Базовое окно свежести 24–72 часа; стартовая настройка сборщика — `LOOKBACK_HOURS=48`, допускается 2–120. Отдельно хранить время публикации, время сканирования, дату будущего/прошедшего события, язык/часовой пояс. Старые публикации только при объективно новом развитии.
- При каждом запуске выбирать **только разрешённые** способы получения: RSS, Atom, API либо допустимая открытая HTML-страница с ограничениями. Сохранять HTTP status, ETag/Last-Modified при применимости, URL, title, publication time, retrieved_at, авторство, исходный допустимый фрагмент, URL канонической публикации, тип первоисточника.
- Проверять `robots.txt` / условия использования, если предполагается регулярный автоматический сбор; поддерживать режим только ручной проверки там, где автоматический доступ спорен. User-Agent с контактной страницей, умеренная частота запросов и backoff.
- Никакого обхода 403, 429, login, paywall и anti-bot. При 429 учитывать Retry-After. Предупреждать об ошибках источников; если недоступен один сайт, остальные продолжают работать.
- Источники должны быть конфигурацией, а не прописанными в промпте. Каждая RSS URL проходит отдельную проверку; имя ресурса само по себе не доказательство доступности фида.

### 6.2 Нормализация и безопасность извлечения

- URL: только одобренные HTTPS-домены, контроль перенаправлений, запрет локальных и частных IP, защита DNS rebinding на уровне фактического TCP-соединения либо документированная безопасная библиотека. Не отправлять произвольные входящие URL к серверу.
- Canonical URL учитывать при доступности, но не объединять разные пути/значимые query-параметры автоматически. Удалять только известные трекеры (`utm_*`, `fbclid`, `gclid`, `yclid` и т. д.). Сохранять original_url.
- Даты приводить с информацией о смещении. Материал без достоверной даты публикации — в ручную очередь, не считать «свежим» молча. Анонс, факт завершённого события и состоявшаяся презентация — разные утверждения.
- Не обрабатывать в LLM код/инструкции веб-страниц как системные команды; маркировать вход как недоверенную цитату/данные, задавать строгий структурный вывод, ограничивать размер.
- Права: исходный текст хранить минимально необходимый объём и срок для проверки; не публиковать дословные переводы защищённых статей или чужие фото/обложки без основания.

### 6.3 Кластеры событий и поиск дублей

Разделить **`source_publication`** (конкретная статья конкретного СМИ), **`event`** (например, релиз определённого альбома) и **`our_article`** (наша редакционная заметка). Пять публикаций об одном альбоме → один сюжет и несколько цепочек подтверждений, а не пять новостей. Следующая значимая стадия события может стать новой заметкой, если ясно указано, **что произошло нового**.

Обязательные стадии дедупликации:
1. Точный URL после допустимой нормализации, source publication ID / GUID, hash исходного содержания.
2. Схожие заголовки, именованные сущности (артист, название альбома, дата), язык/транслитерация, редакционная группа зависимости.
3. Семантическая близость для разных переводов/URL через LLM/эмбеддинги как подсказка, не единственное доказательство. Снизить ложные блокировки.
4. Сверка **не менее 14 дней** архива, затем проверка совпадающего `event_id` и более старых релевантных записей, если доступны. В WordPress 0.3.5 есть точные архивные проверки, но полноценную смысловую проверку должен добавить сборщик.
5. Явные `previous_article_ids`, `development_note`, новый факт с новым source_id при продолжении истории.

При точном дубле блокировать. При вероятном дубле — пометить и предложить человеку объединить/отклонить. Не удалить архивную историю из-за смены названия источника. Повторные запуски в один день должны быть идемпотентными.

### 6.4 Ранжирование и отбор

Для кандидатов оценивать 0–5 и получать `story_score` 0–100:

```
30% — культурная и музыкальная значимость
25% — релевантность аудитории
20% — новизна конкретного повода
15% — достоверность и полнота подтверждений
10% — оригинальность / содержательность

score = 30*significance/5 + 25*relevance/5 + 20*novelty/5
      + 15*evidence/5 + 10*originality/5
```

Высокий score не заменяет фактчекинг. 4–7 достойных историй в дне; обычно ориентир **2–3 Россия + 3–4 мир**, но это не жёсткая квота. Не создавать «заглушки» ради 7 новостей. Допускается неполный черновик со статусом блокировки или сообщение редактору, что достойного выпуска нет. Желательно жанровое разнообразие при сохранении джаза как смыслового центра.

### 6.5 Факты и независимое подтверждение

Должен существовать машиночитаемый реестр: claim ID → точное утверждение → поддерживающие source IDs → дата проверки → тип источника → dependency_group → уровень:
- `verified_primary` — компетентный официальный источник о собственном решении/релизе; не означает независимую музыкальную оценку.
- `verified_independent` — **как минимум две реально независимые редакционные цепочки**, не перепечатки одной PR-заявки.
- `attributed_single` — только один подтверждающий источник; допустимо при ясной атрибуции («как сообщает...») и отдельной проверке человеком.
- `unverified` — утверждение не подтверждено или расходится: блокер; нельзя выводить в читательский текст как установленный факт.

Не проводить «фактчекинг» повторным вопросом той же LLM без доступа к проверенному оригиналу. Каждый факт должен подтверждаться **извлечённым разрешённым материалом**, а не известным модели «по памяти». Сохранять проверяемый trace. Не смешивать дату публикации новости, дату записи альбома, дату выхода релиза, запланированную дату концерта и подтверждённый факт прошедшего мероприятия.

**Обратные свидетельства:** если две публикации противоречат друг другу, фиксировать расхождение и блокер, не усреднять. Мнения критиков — атрибутировать, PR — называть PR. Смерть, здоровье, судебные дела и другие высокочувствительные новости требуют повышенного порога доказательства либо отказа.

### 6.6 Генерация текста и литературная редактура

Текст оригинальный на грамотном современном русском, не калька с английского и не перевод чужой статьи целиком. Стандартный материал 100–180/190 слов (в v2), особо важный — может быть 180–300 слов при содержательном поводе, краткий 60–100. Не раздувать. Заголовок ~6–12 слов: кто/что + действие + суть; лид 1–2 предложения. Основной порядок: главное → детали → контекст → короткое основанное на фактах наблюдение.

Тон сдержанный, образованный, человеческий, музыкально компетентный, **не** излишне хвалебный. Взвешенные авторские замечания допустимы, но отделять вывод от факта. Не писать «потряс мировой джаз», «легендарный», «по-настоящему уникальный», «покорил сердца», «незабываемый», «праздник музыки» без исключительных доказательств. Не изображать собственное прослушивание музыки, если прослушивания не было.

Цитаты только дословные по оригиналу, с точным источником и проверкой контекста; перевод цитаты — явный. Если доступ к цитате ненадёжен — косвенная речь или удалить. Транслитерацию имён перепроверять; названия альбомов и произведений соблюдать; не писать в прошедшем времени о будущем релизе.

**Связь с издателем:** любые заметки о событиях клуба и релизах Jazzist сопровождаются ясной пометкой (например, продюсирование или публикация собственным лейблом). Не выдавать рекламу за независимую критику.

### 6.7 Разделённые роли моделей (программные этапы)

- **LLM-A (лёгкая)**: классифицирует разрешённые фрагменты, определяет сущности и группы событий, формирует первичные структурированные факты. Не пишет окончательные новости.
- **LLM-B (редакторская)**: по подготовленным подтверждённым фактам предлагает 4–7 заметок; ID фактов и источников в JSON, без добавления новых URLs/биографий/цитат.
- **Проверка (не модель одной волей)**: детерминированно сверяет claims с trace; дополнительная LLM может обнаружить противоречия, но не засчитывает доказательства без полученных данных.
- **LLM-C (литературная)**: улучшает русский язык без расширения фактов; любые изменения сущностей/дат запускают возврат к проверке.
- **Программа**: жёстко устанавливает `publication.status=draft`, `edition_number=null`, оценивает schema, проверяет links/claims/dedup, добавляет блокеры, импортирует только в разрешённом режиме.

У всех стадий: детерминированные входы/выходы и версии промптов; допуски по токенам/стоимости, timeout, retries с ограничением, журнал ошибок без секретов, fallback на отчёт вместо ложных данных.

**Важные URL**:

| Назначение | URL |
|---|---|
| Главная газеты | `https://kozlovclub.ru/gazeta/` |
| Выпуск | `/gazeta/YYYY-MM-DD/` |
| Отдельный материал | `/gazeta/material/YYYY-MM-DD-article-id/` |
| Архив | `/gazeta/archive/` и `/gazeta/archive/page/2/` |

| Приватный предпросмотр | `/gazeta/preview/ID/` + nonce, без публичного доступа |

| Последний публичный выпуск (GET) | `/wp-json/ezhednevny-standard/v1/latest` — **только публичная проекция** |
| Админка газеты | `/wp-admin/admin.php?page=es-newsroom` |
| Режим/остановка | `/wp-admin/admin.php?page=es-runtime` |

**Строгий REST-контракт 0.3.5**:
- HTTPS + WordPress Application Password **отдельного импортёра**, Basic Auth поверх HTTPS, роль `es_import`.
- `Content-Type: application/json`. Стандартный POST — только для `draft`. Максимум **256 КиБ**; JSON глубина не более 32; для полного номера 4–7 статей, черновик может быть 0–7.
- Максимум 12 источников/статью, 40 claims, 40 абзацев, 10 цитат. Валидация отклоняет неведомые поля, неподдерживаемую разметку, неверные права/статусы.
- На сервере не более 10 POST импортов в минуту на одного пользователя.
- Идемпотентность по содержимому и `import_id`. Другая полезная нагрузка с повторным `import_id` → 409. Обновление версии при допустимой автоматической правке — с `If-Match: "числовая_версия"`, без него → 428, устаревшая → 409.
- Если редактор хотя бы раз коснулся выпуска (`human_touched`) или выпуск когда-либо публиковался, **обычный REST/автоматический импорт не может его перезаписать**. Ответ конфликта — остановить, не пытаться передать чужие полномочия или параметр `force`.
- Возвращаемый JSON импорта: `{"id":123,"version":1,"status":"draft","unchanged":false}`; ETag с версией. **Маршрута REST для публикации нет**.
- Только владелец через авторизованную admin-форму может явно заменять когда-либо не публиковавшийся существующий черновик, после diff и резервной редакции; это **не** API для сборщика.
- Номер выпуска присваивает WordPress только при первой ручной публикации; не придумывать номер в JSON. Дата уникальна.

**Режимы**: `closed` (видит только редакция), `public` (открыты одобренные), `paused` (запрет чтения и записи в газету). В closed не выдавать страницы через общий HTML-кэш. Раннее аварийное отключение: файл `wp-content/plugins/kozlov-jazzeta/DISABLE-GAZETA` либо флаг `KOZLOV_GAZETA_DISABLED`; если нужно — переименовать **только** папку `kozlov-jazzeta`, не всю `plugins`.

**Кэш:** при закрытом пилоте исключить **внешними правилами кэша**, проверенными на сервере, `/gazeta/*`, preview/query-варианты, собственный REST namespace из full-page HTML cache/CDN (не отключать общий кэш всего сайта). Для публичных авторизованных ответов `private/no-store/Vary Cookie`; для предпросмотра всегда noindex/no-store. Кэш до запуска WordPress может обойти защиту заголовков плагина — тестировать реально из анонимного браузера и через CDN.

**SEO:** title, description, canonical, robots, OG/Twitter/JSON-LD, sitemap должны соответствовать именно виртуальному газетному маршруту, не посту WordPress «за ним». Не дублировать title/canonical/robots, не ломать Yoast/verification. В публичном режиме сохранить Google/Яндекс-вебмастер метатеги и Organization/WebSite, без ложных Article/Breadcrumb стороннего query. Интеграцию аналитики выполнять один раз, не дублировать pageview. Сохранять штатные `wp_head`, `wp_body_open`, `wp_footer`, панель WP авторизованным пользователям; не добавлять JS в JSON выпуска.

**Дизайн:** классическая газетная эстетика из `ezhednevny-standart-design.html` и версия 0.3.5 с **родными** header/footer темы KozlovCLub, логотипом, меню, поиском, календарём и мобильной навигацией. Газетные CSS внутри `#es-newspaper`, не влиять на афишу. Визуальные ориентиры прототипа: тёплая бумага `#f3f0e7`, тёмный текст `#191d1b`, тёмно-зелёный фон `#152320`, бордовый акцент `#8b352d`, антиква Georgia/Times, аккуратные газетные колонки, линейки, чёткая иерархия. Не возвращаться к кустарной самодельной «шапке сайта» и не менять реальную тему. A−/A+ на читательских текстах, 100%, 90–140%, ночной режим. Адаптивность 320/390/768/1440 px.

## 8. Схема обмена JSON 1.1 — реализовать именно её

**Источник истины:** копия `schemas/issue.schema.json` из `kozlov-jazzeta-0.3.5.zip` приложена целиком ниже. Старый `editorial/issue.schema.json` — историческая редакционная схема, проверять различия с рабочей `schemas/`.

Верхний уровень:
```
{
  "schema_version": "1.1", "import_id": "auto.YYYY-MM-DD.contenthash",
  "edition_date": "YYYY-MM-DD", "timezone": "Europe/Moscow",
  "edition_number": null, "publication": {"status":"draft"},
  "articles": [/* 0–7 строгих article */],
  "social": [/* максимум 5, каждая соответствует article */],
  "editorial": {"ready_for_human_review": false,
                "blocking_issues": ["..."],
                "source_scan_window_start": "ISO8601 offset-aware",
                "source_scan_window_end": "ISO8601 offset-aware",
                "generation_notes": ["..."]}
}
```

Каждая статья: `id`, `region`, `category`, `placement`, `headline`, `lead`, `body_paragraphs`, `summary`, `event_date`, `story_group_id`, `event_id`, `story_score`, `sources[]`, `claims[]`, `quotes[]`, `conflict_disclosure`, `editorial_notes[]`, `media_rights`, а при продолжении истории `previous_article_ids[]`, `development_note`. `sources[]`: `id,title,publisher,url,published_at,type,verification_checked_at,dependency_group`, при наличии `publication_id/content_hash`. `claims[]`: `id,statement,verification,source_ids[],editorial_note`. `social[]`: `article_id,telegram_sentence,instagram_sentence,visual_format:"1080x1350"`.

**Никаких дополнительных JSON полей по инициативе модели** — рабочий валидатор их отвергнет. Должна быть именно schema 1.1, а также реальная WordPress PHP-валидация и проверки связей/прав, не только клиентское `jsonschema`.

Из-за безопасности следует конструировать неизменяемые поля (`status`, номера, источник URL из доверенной очереди) программно, не брать их из фантазии LLM. `ready_for_human_review` можно выставлять true **только** после реальных машинных проверок и снятия блокеров по согласованным правилам; человеческие подтверждения при этом остаются пустыми и публикация невозможна.

## 9. Beget: развертывание, настройки и расписание

### 9.1 Размещение

`~/ezhednevny-standard-beget-collector-0.1.0/` — отдельная директория аккаунта Beget, **вне** `kozlovclub.ru/public_html` и прочих публичных каталогов. Внутри изолированные `collector.py`, `run.sh`, `config`, `data`, `logs`; `.env` права 0600; директории с результатами не доступны по HTTP. Никаких открытых конечных точек управления секретами.

На хостинге проверить `python3 --version`, `zoneinfo`, DNS, исходящий HTTPS к одобренным сайтам и Beget Gateway, скорость, лимиты времени/CPU/памяти и доступность CronTab. Если виртуальный тариф не выдерживает — предложить технически оправданный отдельный сервер/процесс, **не переносить** боевой WordPress на VPS без отдельного решения. Возможный удалённый VPS для международных публичных источников допустим только как согласованная инфраструктура, а не способ обхода `robots.txt`/403/429.

### 9.2 ИИ-шлюз

Base URL: `https://api-llm.beget.com/v1`; API `GET /v1/models` для актуальных IDs и тарифов. Отдельный секрет для газеты; модель для лёгкой классификации, отдельная для написания по результатам бенчмарка качества/стоимости; задавать `max_tokens`, таймауты и budget. Первоначальный тестовый бюджет можно держать на уровне **500 ₽/мес как предложенный лимит пилота**, но он не является согласованной оценкой реальной стоимости эксплуатации и зависит от объёма/моделей.

Важно: Beget AI Gateway — **только прокси к LLM**, не поисковая система, не робот обхода источников и не фактчекинг. Сбор/проверка/дедуп — обязанности нашего кода.

### 9.3 Очередь запуска / cron

Сейчас в стартовом `run.sh` поддерживается `scheduled`: безопасный вариант расписания Beget `0 * * * *` + проверка внутри программы, что в `Europe/Moscow` сейчас 08:00–08:59; запуск реально один раз за московские сутки через lock/marker. Альтернатива — отдельная точно настроенная задача 08:00 МСК только после подтверждения часового пояса Cron сервера. Не копировать «0 8 * * *» в неизвестном часовом поясе.

Сначала проводить `check`, `collect`, `generate`, `validate`, `daily` с выключенным импортом. Только после E2E-теста включать `ENABLE_WP_IMPORT=1` и расписание. Никогда не использовать HTTP-крон, запускающий публичный веб-URL без строгой аутентификации. Скрипт должен сохранять checkpoint и status: не тратить ИИ-запрос повторно, не создавать повторный номер, не блокировать другие сайты. Логировать длительность, количество полученных записей, error types, токены/cost, идентификатор выпуска; **не** логировать ключи, Basic Auth, приватные исходники.

### 9.4 Контроль расходов / отказоустойчивость

- Сначала измерить стоимость реального пилотного материала по токенам, затем выбирать модель. Сравнивать полную стоимость номера и долю отклонённых LLM ответов, а не красивое название модели.
- Ограничить ключ и `max_tokens` на стороне Beget; локально месячный budget guard, превышение → остановка до действия человека.
- Если 1–3 RSS источника упали, сохранить частичный отчёт с ошибками. Если нет качественных кандидатов или сетевых прав — не выдумывать новости, не дёргать дорогую модель впустую.
- Ограниченные ретраи с джиттером для временных 5xx/timeout и уважением к Retry-After; ошибки 401/403 и блокеры лицензий не лечить повтором.
- Порядок действий при сбое: журнал → уведомление редактору (только согласованный приватный канал) → сохранение предыдущего опубликованного номера → ручное расследование.

## 10. Поведение конкретного редактора / владельца

Редакторский процесс проектировать максимально коротким и понятным:
1. Открыть «Ежедневный стандарт» в WordPress и увидеть «Номер на сегодня: черновик, X статей, Y блокеров» и состояние сбора.
2. Для каждой статьи — заголовок, текст, утверждения и реальные источники, точные даты, предупреждения о повторе, возможность правки/отклонения.
3. В отдельных статусах показывать «прислано источником», «проверено первоисточником», «подтверждено независимо», «не проверено»; не писать зелёное «проверено», если было только LLM мнение.
4. После исправлений и снятия блокеров подтвердить каждый материал, посмотреть предпросмотр и карточки.
5. Только владелец даёт итоговое согласие и нажимает «Опубликовать выпуск». Публикация — отдельное, явное действие в WP, не входящее в Cron/AI/API.
6. Отредактированный человеком черновик закрыт от автообновления. Если владелец сознательно хочет заменить его полным JSON — уже существующий в 0.3.5 **ручной** трёхэтапный диалог с diff и резервной версией; не автоматизировать эту форму.

Безопасное удобство: автоматический сборщик может создать отдельный **отчёт об изменениях сюжета** или предложить материалы на завтра, но не может незаметно заменить текущую ручную редакцию. При невозможности импорта сохранять локальный JSON и показывать причину в журнале.

## 11. Карточки и соцсети

Формат соцкарточки **1080×1350 px (4:5)**, классическая типографика газеты. До пяти историй, не выдумывать пятую. Telegram — лаконичная новость 1–2 предложения + постоянный URL опубликованной статьи; дайджест с заголовком выпуска и ссылками. Instagram — **одно самостоятельное предложение** без кликбейта, фото только с правами. Исходный WP-плагин уже умеет PNG-карточки и текстовый дайджест; проверить качество, кириллицу, длинные заголовки, отображение номера/даты и реальные публикационные ссылки. **Автопостинг в Telegram/Instagram не включать**, пока владелец отдельно не поставит такую задачу и не утвердит правила.

## 12. Показатели качества, мониторинг и журнал

Минимальный dashboard состояния отдельного сборщика (можно CLI/отчёт, не обязательно сразу новый UI):
- `last_run_at`, длительность, `run_id`, версия кода и промптов, дата/окно сбора;

Результат каждой стадии должен объяснять, **почему** статью взяли или отклонили. Не превращать журнал в хранилище чужих полных статей. Установить retention для промежуточных фрагментов, логи без секретов, ротацию и резервирование локальных конфигов/черновиков.

## 14. Сценарии обязательных тестов

Ниже минимум. Для каждого теста: шаги, вход, ожидаемое, фактическое, среда, доказательство, PASS/FAIL.

1. RSS 200, RSS без даты, Atom, битый XML, HTML вместо XML, очень большой ответ; локальные адреса и redirect, DNS-трюки, 403, 404, 429 Retry-After, 500, timeout.
2. Два источника одного пресс-релиза: один dependency_group, статус independent запрещён. Независимое первичное сообщение + независимая редакция — возможное подтверждение, если факты совпадают.
3. Те же ссылки с UTM/AMP/query: избежать ложных повторов и ложного объединения разных историй. Внутренние и междневные дубли, семантический дубль разного языка, продолжение с реальным новым фактом.
4. Запланированная дата выхода через 2 дня — «выйдет», не «вышел»; релиз неделю назад с новым событием — отличать повод. Публикация источника без timezone, противоречащие даты.
5. LLM выдумывает URL, автора, цитату, прослушивание пластинки, лицензированную фотографию или «verified_independent» — валидатор/конвейер должен это отклонить или направить на проверку, никогда не принять без исходного доказательства.
6. WordPress импорт: валидный draft → 201; точный повтор → 200 unchanged; неправильный Content-Type → 415; слишком большой → 413; нет прав → 403; новые данные без If-Match → 428; конфликт версии → 409; перезапись ручного/опубликованного → отказ.
7. Одновременный cron дважды, сеть падает после успешного POST, повтор в полночь МСК, повреждённый marker/log, закончившийся месячный бюджет. Нельзя публиковать второй номер или бесконечно платить за повторы.
8. W3 TC/CDN: аноним не видит закрытый выпуск, не видит чужую WP-панель, не видит предпросмотр; публичное снятие не остаётся закэшированным. Проверить query URLs и `latest`.
9. Mobile 320/390/768/1440, 140% текста, длинные заголовки, русский текст, невстроенные шрифты, реальная тема/меню, sitemap/canonical/OG и корректные ссылки из карточек.
10. Аварийное отключение отдельного сборщика и отдельного газетного плагина; основной сайт продолжает работать, данные/история сохраняются.

## 15. Чёткие критерии завершения проекта

**Можно считать автоматическую подготовку черновиков готовой**, когда:
- разрешённые рабочие источники проверены и задокументированы; собственные сетевые ограничения соблюдены;
- за 10 подряд тестовых дней произведены осмысленные редакционные результаты без скрытых вымышленных фактов и дублей;
- все существенные факты снабжены правильной атрибуцией и проверочным trace; источник и время доступны редактору;
- JSON 1.1 проходит жёсткую валидацию, WordPress импортирует draft и сохраняет историю; ручная редакция никогда не уничтожается автоматом;
- единственная публикация — вручную выбранным владельцем;
- кэш/предпросмотр/SEO/панель/мобильная тема проверены на целевом стеке; эффект на афишу и продажи билетов отсутствует по проведённым проверкам;
- Beget Cron отрабатывает, ключ ограничен, себестоимость выпуска измерена, известен способ остановки, восстановления и уведомления об ошибке;
- созданы ZIP-артефакты и воспроизводимые тестовые протоколы, ограничения сформулированы честно.

**Нельзя объявлять готовым**, если готов только HTML-макет, прошли только локальные unit-tests, включены 2 непроверенных RSS-примера, модель выдаёт 5 красивых, но недоказанных статей, API-ключ без лимитов, на production не проверен кэш, или кто-то предлагает «для простоты» автоопубликовать.

## 16. Что именно Claude должен выдать заказчику при продолжении разработки

**В первом ответе после чтения этого ТЗ и двух ZIP:**
- сжатый вывод о состоянии и обнаруженных расхождениях между сборщиком 0.1.0 и WordPress 0.3.5;
- конкретный план исправлений первой очереди без изменения сайта;
- реестры источников и этапы проверки RSS; не придумывать результаты сетевых запросов;
- какие файловые/сетевые доступы действительно нужны и для чего; не просить пароль администратора и не требовать все ключи в чат;
- конкретный ZIP следующей версии и отчёт об автономных тестах, если код и окружение доступны;
- подробный пошаговый план включения на Beget и rollback.

**По каждой итерации:** `CHANGELOG.md`, `SECURITY.md` (угрозы, меры, известные границы), `TEST-REPORT.md` (что проверено, где, результат), `DEPLOY.md` (миграции, настройки, dry-run, backup, rollback), `CONFIG.example`, обновлённые источники с проверенными статусами, архив ZIP с точной версией и SHA-256. При непрохождении тестов выпуск ZIP не рекомендовать к установке на продакшн.

Если нет доступа к настоящему Beget / WordPress / модели, не утверждать, что они протестированы; подготовить команды и точный сценарий, который владелец сможет выполнить или предоставить через отдельную управляемую сессию. Включение Cron, новых ключей и prod deployment — только с согласия владельца.

````markdown
# ЕЖЕДНЕВНЫЙ СТАНДАРТ
## Редакционная политика и техническое задание для ИИ-редакции · версия 1.0

**Дата утверждения концепции:** 21 октября 2026 года  
**Статус:** утверждаемая спецификация; не запущенная автоматизация  
**Издатель:** Клуб Алексея Козлова  
**Часовой пояс выпусков:** Europe/Moscow

## 1. Миссия и характер

«Ежедневный стандарт» — ежедневная русскоязычная музыкальная газета о джазе и близкой ему музыкальной культуре. Читатель за 3–5 минут получает достоверную картину важных событий: что произошло, почему существенно, где прочитать или послушать первоисточник.

**Голос издания:** осведомлённый, интеллигентный, сдержанный. Не пресс-релиз, не академический бюллетень, не авторский блог со множеством оценок. Авторский вывод допустим, если помогает понять событие и обоснован фактами. Доля интерпретации обычно невелика — ориентировочно до 10–20% текста, но не является механической квотой.

**Визуальный язык:** классическая качественная газета, тёплая бумага, чёрный набор, тёмно-бордовый акцент, выразительная антиква, иерархия полос. Не карикатурная ретро-стилизация и не перегруженный веб-дизайн.

## 2. Тематика и границы

### Включаем

- Джаз: традиционный, современный, авангард, фьюжн, джазовый вокал, новые записи, архивные находки.
- Блюз и блюз-рок: например, Eric Gales, Marcus King, Buddy Guy, Gary Clark Jr., Derek Trucks, Joe Bonamassa.
- Фанк, соул, R&B и смежные сцены: например, MonoNeon, Cory Wong, Snarky Puppy и музыкальные проекты, связанные с этими направлениями.
- Рок и гитарная музыка — если это содержательный музыкальный сюжет: Eric Clapton/Crossroads, Mark Knopfler, известные музыканты-сотрудники джазовой или блюзовой сцены, новые художественные подходы.
- Фестивали, конкурсы, выставки и музыкальные инструменты: Crossroads Guitar Festival, Guitar Summit, NAMM, важные премьеры оборудования, исследования звучания.
- Музыкальная наука и технологии: избирательно, в том числе исследования из arXiv, с явным различием между препринтом и опубликованной рецензируемой работой.
- Российские события, региональная сцена и новые музыканты — на равных правах с международными именами.

### Исключаем

- Сплетни, светскую хронику, необоснованные слухи, списки без новостного повода, коммерческие пресс-релизы без реальной музыкальной значимости.
- Большинство рядовых анонсов туров и массовых товаров без существенного повода.
- Автоматическую публикацию каждого релиза артиста только потому, что он знаменит.
- Саморекламу клуба, маскируемую под независимые новости.

## 3. Источники

**Стартовый каталог:** 30 присланных конкретных URL: 17 зарубежных СМИ, 8 российских СМИ, 5 музыкальных лейблов. Описание «34 источника» не соответствует фактически присланным URL. Программа должна принимать расширение каталога и находить официальный первоисточник за его пределами. Каталог хранится отдельно от редакционных промптов.

**Типы источников:** официальный артист/лейбл/фестиваль; независимая редакция; пресс-служба/PR; платформа релизов; исследование/препринт; афиша/расписание; пользовательское сообщение. Тип влияет на доверие к утверждению, но не подменяет проверку.

**Приоритет доверия:** официальный первоисточник для собственных заявлений, документов и анонсов; затем независимое профильное СМИ; затем другие редакции и отраслевые сайты. PR-материал не превращать в независимую оценку качества. Перепечатки одного пресс-релиза объединять в одну группу зависимости.

**Доступность и права:** наличие URL в каталоге не гарантирует работающий RSS, разрешённость автоматического получения полного текста или лицензию на фотографию. Для каждого домена хранить стратегию доступа; соблюдать ограничения сайта и разумную частоту запросов. Не обходить закрытые материалы и не публиковать полные переводы защищённых статей.

## 4. Производственный цикл

1. **Сбор:** получить записи из разрешённых RSS/API/открытых страниц и официальных анонсов. Сохранять URL, дату публикации, время сбора, заголовок, автора, медиа и текст только в допустимом объёме.
2. **Нормализация:** привести даты и часовые пояса, канонические URL, имена, названия, язык, категорию и регион к единым форматам. Сохранить оригинальную формулировку источника.
3. **Группировка:** выделить события и истории. Один альбом, о котором написали пять сайтов, — один сюжет. Сравнивать с архивом как минимум за последние 14 дней; повторы допускать только при новом значимом факте.
4. **Отбор:** оценить музыкальную ценность и релевантность; выбрать 4–7 достойных сюжетов при достаточной повестке.
5. **Проверка фактов:** установить происхождение существенных утверждений, даты события и публикации, независимость свидетельств, правильное написание имён.
6. **Написание:** создать оригинальную заметку по фактам — не транслировать композицию и фразы исходной статьи. При англоязычном источнике выполнить редакторский перевод фактического содержания.
7. **Редактура:** отдельно проверить текст, литературный стиль, авторские суждения, цитаты, отсутствие внутренних инструкций и повторов.
8. **Сборка:** сформировать выпуск в JSON, социальные выжимки и карточки; сохранить редакционный журнал.
9. **Контроль:** провести программные проверки схемы, ссылок и полноты доказательств. Создать **только черновик** в WordPress.
10. **Человек:** ответственный редактор правит или удаляет заметки и отдельно нажимает «Опубликовать выпуск». ИИ не может инициировать это действие.

## 5. Приоритеты, баланс и новизна

Для каждого кандидата присваивать значения 0–5 и рассчитывать балл 0–100:

- Музыкальная и культурная значимость — 30%.
- Релевантность читателю «Ежедневного стандарта» — 25%.
- Новизна информационного повода — 20%.
- Достоверность и полнота свидетельств — 15%.
- Оригинальность/содержательность сюжета — 10%.

Формула: `score = 30*significance/5 + 25*relevance/5 + 20*novelty/5 + 15*evidence/5 + 10*originality/5`.

**Редакционные ограничения:** подтверждение фактов — независимый обязательный фильтр, а не сумма баллов. Никакая высокая оценка не легализует ложный факт.

**Размер:** целевой диапазон 4–7 новостей в день; обычно 2–3 российских и 3–4 международных. В редкий день с четырьмя достойными сюжетами выпускать четыре. Не выдумывать новости для заполнения квот; допустимо задержать выпуск и сообщить редактору, что повестка недостаточна.

**Разнообразие:** джаз — смысловой центр, но новость о значимом блюзовом музыканте, Guitar Summit или Crossroads может быть главной. При равной значимости предпочтение свежему, необычному и недостаточно освещённому сюжету, особенно российской сцене.

**Временное окно:** приоритет значимым событиям и публикациям последних 24–72 часов; старые публикации допускаются, если появился новый повод. Дату опубликованного сообщения и дату произошедшего/запланированного события хранить раздельно.

## 6. Проверка по утверждениям, не по статье целиком

У **каждого существенного утверждения** есть ID и ссылки на источники. Статусы:

- `verified_primary` — достоверно удостоверено компетентным первоисточником о его собственном событии/решении (например, лейбл анонсирует свой релиз).
- `verified_independent` — подтверждено независимыми качественными источниками с разными информационными цепочками.
- `attributed_single` — один источник; публиковать при наличии оснований с формулой «по сообщению…» и редакторской проверкой.
- `unverified` — источник не подтверждает факт, данные расходятся или проверка не проведена: не подавать как факт; поместить в отчёт редактору и блокировать самостоятельный допуск.

При противоречиях указать их подробно в приватном отчёте. Нельзя объявлять два URL «двумя независимыми источниками», если оба пересказывают один пресс-релиз.

**Цитаты:** подлинник дословно, с привязкой к исходному URL и контексту. Русский перевод цитаты допустим только после проверки оригинала; не менять модальность и эмоциональную окраску. При отсутствии доступа к точной цитате — только косвенная речь с атрибуцией либо убрать фрагмент.

**Научные материалы:** препринт — не доказанный научный консенсус. Проверять ссылку, авторов, версию, дату, метод, ограничения, не обещать практических результатов без данных.

**Репутационные и высокочувствительные сюжеты:** смерть, болезнь, преступление, обвинения, финансовые проблемы — только с достаточными надёжными свидетельствами; при сомнениях не публиковать.

## 7. Стиль текста

**Заголовок:** обычно 6–13 слов. Предмет + действие/суть; образность умеренна; не прятать событие ради интриги. Не писать капслоком весь текст.

**Лид:** 1–2 предложения; кто, что, когда и почему заслуживает внимания.

**Тело:** факт → важная деталь → контекст → при наличии оснований короткое наблюдение. Основная история обычно 180–300 слов; обычная заметка 100–190; короткая 60–100. Не растягивать материал ради длины.

**Язык:** живой литературный русский; минимум канцелярита и англицизмов там, где есть точные русские эквиваленты. Разные ритм и синтаксис, никакого механического «в рамках», «подарил поклонникам», «взорвал сцену». Не использовать рекламные оценки в собственном голосе.

**Перевод:** свободная редакторская передача фактов, а не пословный перевод и не пересказ чужой статьи в её структуре. Музыкальные названия, имена, даты, источники — точные. Неясную транскрипцию уточнять, не угадывать.

**Авторская мысль:** разрешается аккуратный, доказуемый вывод (обычно одно-два предложения). Это интерпретация, не факт. Нельзя утверждать слышимые особенности записи, если система не анализировала аудио и не цитирует рецензента с обозначением его мнения. Формулировка «для сцены это значимое событие» должна объяснять почему.

**Запреты:** вымышленные детали, цитаты и реакции; слова «легендарный», «гениальный», «сенсационный», «культовый» без серьёзных оснований; «потряс мир», «покорил сердца», «невероятная энергетика», «звёздная россыпь»; длинные академические обороты и избыточная эмоциональность.

**Связи с издателем:** концерты Клуба Козлова, релизы Jazzist или проекты, связанные с редакцией, сопровождать ясным раскрытием отношений; сохранять редакционную ценность независимо от этого.

## 8. Уровни выпуска и газетная иерархия

- **Первая полоса:** одна главная история (не обязательно джазовая, не обязательно зарубежная).
- **Остальные материалы:** равноправная иерархия по значимости — крупный второй материал, несколько обычных заметок, возможно краткая заметка.
- **Рубрики:** «Россия», «Мир», «Новые записи», «Люди и сцена», «Блюз и гитара», «Фестивали», «Инструменты», «Ноты будущего». Рубрика — навигация, а не квота.
- **Архив:** каждый номер и отдельная статья в будущем должны иметь постоянный URL. Новые номера не переписывают историю старых.

## 9. Instagram и Telegram

- Выбирать **до пяти** историй из опубликованного номера; при наличии всего четырёх материалов не создавать пятую искусственно.
- Telegram: вводная строка «Ежедневный стандарт · дата», пять (или меньше) односентенционных новостей, ссылки на собственные материалы и номер; желательно без повторяющихся эмодзи и кликбейта.
- Instagram: до пяти карточек 1080×1350 (4:5), единый утверждённый газетный дизайн. На каждой заголовок и одно самостоятельное ёмкое предложение, дата, номер и название рубрики; фотографии только при ясных правах.
- Соцверсии генерируются **после** утверждения содержательных фактов, ссылки на сайте — только на реально опубликованные страницы.
- Нельзя писать в карточке то, чего нет в утверждённой статье.

## 10. Машинный интерфейс и публикация

Результат **валидный JSON**, соответствующий файлу `issue.schema.json`. Каждая заметка хранит источники, дату публикации источников, дату события, факты со статусами, читательский текст, рубрики, регион, оценку приоритета, раскрытия связи с издателем, приватные замечания редактора и картографию права на изображения. Соцматериалы хранятся отдельно.

**Запрет автоопубликования:** API-процесс имеет право создавать/изменять только черновики газеты. Статус `publish` не принимает от LLM. Номер присваивает сервер; уникальность даты выпуска обеспечивает база данных. Редакторское действие публикует материал только после проверки. Не отправлять в API персональные и секретные данные.

**Сбои:** при недоступности одной модели пробовать настроенную замену, логировать ошибку и расход; при нехватке источников/расхождении фактов — создавать неполный отчёт, а не имитировать выпуск. Полный повтор запуска за ту же дату обновляет черновик, а не создаёт двойник. Соблюдать размер запросов и `max_tokens`.

## 11. Раздельные задания моделям

**Этап A, дешёвая LLM:** классификация, извлечение фактов, определение жанров, группировка по сюжету. Вход: допустимые данные источников. Выход: структурированные кандидаты, без готовых новостей.

**Этап B, редакторская LLM:** выбрать 4–7 историй, подготовить исходный заголовок, лид и статью; все утверждения снабдить ID факта. Выход: черновик, без публикации.

**Этап C, независимая проверка:** через программно полученные страницы сопоставить каждое утверждение с первоисточником. Модель не должна утверждать «проверено», если у неё нет сохранённого оригинала или выдержки. Критические расхождения -> редакторский блокер.

**Этап D, литературный редактор:** полировка русского языка без добавления фактов. Если хочет исправить фактическую часть — отправить на дополнительную проверку, а не тихо изменять.

**Этап E, программа:** валидация JSON, контроль прав, источников, изображения, схожести с прошлым номером, создание черновика WordPress; никаких прав на публикацию.

## 12. Минимальные условия приёмки

1. В каждом опубликованном материале все существенные факты имеют проверяемые источники и статус проверки.
2. Ноль выдуманных цитат, URL, имён, дат, событий или прослушанных впечатлений.
3. Нет повторов сюжета внутри выпуска и повторов без нового повода в архиве.
4. Ссылки и оригинальные публикации проверены на момент формирования черновика; недоступность после этого не скрывается.
5. Нет технических указаний или внутренних пометок в читательском тексте.
6. Раскрыты связи с клубом/лейблом и права на иллюстрации.
7. Номер не публикуется роботом ни при каких обстоятельствах.
8. Минимум 10 подряд тестовых выпусков проверены редактором; все найденные фактические ошибки устранены до запуска автоматической подготовки ежедневных черновиков.
````

## D. Системный промпт редактора v1 (исходный файл проекта)

```text
РОЛЬ
Ты — главный редактор русскоязычной газеты «Ежедневный стандарт», издатель — Клуб Алексея Козлова. Ты готовишь черновики новостных выпусков о джазе, блюзе, фанке, соуле, фьюжне, содержательной гитарной музыке, музыкальных фестивалях, инструментах и технологиях. НЕПЕРЕСТУПАЕМЫЕ ПРАВИЛА
1. Используй ТОЛЬКО факты из полученных проверяемых источников и из явно помеченного справочного редакционного контекста. Не выдумывай актуальные события, даты, названия, цитаты, URL или имена. Если материала недостаточно — верни недостаточность данных, а не сочиняй выпуск.

3. Каждый существенный факт привяжи к ID источника и отметь один статус: verified_primary, verified_independent, attributed_single, unverified. Утверждение может иметь verified_primary при наличии одного компетентного первоисточника о собственном анонсе. Две перепечатки одного пресс-релиза не являются независимой проверкой.
4. Запрещены ложные утверждения «я проверил ссылку», «я прослушал запись», «я прочитал полный текст», если эта операция не отражена во входных данных. Отсутствующий оригинал или сомнительная цитата — блокировка или косвенная речь без прямой цитаты.
5. Никогда не превращай рекламный отзыв артиста или лейбла в самостоятельное мнение газеты. Не перепечатывай охраняемые статьи и не создавай их полноценные переводы: пиши новый русский текст по установленным фактам, сохраняя ссылки и атрибуцию.
6. Не публикуй новости про сам клуб или связанный лейбл без явного раскрытия отношения к издателю. Раскрытие должно быть видно читателю, а не только редактору.
```

````markdown
# Редакционный стиль: утверждаемые правила

1. **Тон:** точный, интеллигентный, спокойный, музыкально компетентный. Без канцеляризма и показной поэтичности.
2. **Заголовок:** деятель + действие + главный смысл; 6–12 слов ориентировочно. Интрига возможна, но факт не скрывать.
3. **Лид:** 1–2 предложения; отвечает на вопросы кто, что, когда и почему значимо.
4. **Заметка:** обычно 100–180 слов; главная новость → контекст → важная деталь → спокойное завершение. Длиннее только если того требует событие.
5. **Перевод:** не пословный, а редакторский. Сохранять смыслы, даты, имена, оттенки неопределённости; не добавлять авторских оценок, которых нет в источнике.
6. **Цитаты:** дословные — только после сверки с оригиналом; переводные цитаты явно обозначать как перевод. При сомнении использовать косвенную речь.
7. **Музыкальные характеристики:** «музыка с напряжённой ритмикой» — только после прослушивания или с явной атрибуцией автору/критику. Пресс-релиз не превращается в независимую рецензию.
8. **Достоверность:** отдельно отмечать «подтверждено по первоисточнику», «подтверждено независимыми источниками», «только одно сообщение», «не подтверждено»; не выдавать количество ссылок за количество независимых источников.
9. **Время:** строго различать анонс, выход и состоявшееся событие. В конце октября 2026 года события 20 октября нельзя автоматически описывать как состоявшиеся только по старому анонсу.
10. **Связанные материалы:** всякий конфликт интересов издателя отмечать читателю в конце новости, включая релизы собственного лейбла и мероприятия своего клуба.
11. **Telegram:** одна информативная фраза, можно две при необходимости; новость вместе со ссылкой на полный материал.
12. **Instagram:** ровно одно предложение, читаемое отдельно от иллюстрации; без интриги ради клика и без непроверенных превосходных степеней.
13. **Запрещены:** «потряс музыкальный мир», «по-настоящему уникальный», «взорвал сцену», «звёздный состав» без контекста, «покорил сердца», «незабываемый», «настоящий праздник джаза».
14. **Редакционные факты:** автора, число источников, историю правок, полученные лицензии на изображения и исходный URL сохранять в метаданных, не смешивать с читательским текстом.
````
